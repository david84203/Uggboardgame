# 03 · 臉部圖解（腮紅 / 修容 / 打亮位置）前端渲染策略

問題：報告要呈現「針對該臉型」的腮紅、修容、打亮位置圖解。有三條路：

| 方案 | 做法 |
|---|---|
| **A. AI 動態生成圖片** | 把臉型與建議餵給影像生成模型，直接產出示意圖（或在客人照片上生成） |
| **B. AI 回傳標籤 → 前端匹配預製圖庫** | AI 只回傳代碼（`face_shape.type`、`blush.placement`、`contour.zones`…），前端用預先畫好的 SVG 圖層組合 |
| **C. 特徵點參數化疊圖（B 的進階）** | 客端用 MediaPipe Face Landmarker 取得 468 個臉部特徵點，把 B 的圖層以參數方式貼到**客人自己的照片**上 |

---

## 1. 三方案比較

| 面向 | A. AI 動態生成 | B. 標籤 → 預製圖庫 | C. 特徵點參數化疊圖 |
|---|---|---|---|
| 每次成本 | 高（影像生成每張 $0.04–0.2，且常要生成 3 張） | **≈ 0**（靜態資源） | ≈ 0（wasm 在客端跑） |
| 延遲 | 10–40 秒，疊在分析之後 | **0**，報告一到即渲染 | 客端 100–300ms |
| 一致性 / 品牌感 | 每次不同、風格漂移、可能畫錯位置或產生詭異臉 | **完全可控**，設計師畫一次全站一致 | 可控（圖層仍是設計師畫的） |
| 正確性 | 生成模型不理解「修容在下顎角」這種空間指令，錯誤率高 | 由專業（Han）定義每個臉型的畫法，**專業背書** | 同 B，且位置隨真臉調整 |
| 個人化程度 | 高（若用客人照片）但不可靠 | 中（通用臉型示意圖） | **高**（畫在客人臉上） |
| 個資風險 | 高：照片要送到生成模型、可能被留存 | **最低**：不需要照片 | 低：特徵點在客端算，不出裝置 |
| 開發量 | 低（呼叫 API）但除錯無底洞 | 中：設計 6 套 × 3 層 SVG + 對照表 | 高：特徵點對齊、透視、髮際遮擋處理 |
| 可互動 | 否（點陣圖） | **是**：圖層開關、hover 說明、動畫 | 是 |
| 離線 / 可快取 | 否 | 是（SVG 隨 bundle） | 需載 wasm（~2MB，可快取） |
| 失敗模式 | 生成失敗 / 內容審核擋下 → 報告缺圖 | 幾乎不會失敗 | 特徵點偵測失敗 → 退回 B |

## 2. 建議

**MVP 採 B，Phase 2 加 C（以 B 為 fallback）。不採 A。**

理由：
1. 這個功能的價值在「專業的畫法」而不是「AI 會畫圖」。畫法由 Han 定義，AI 負責判斷「你是哪一型」，圖庫負責「這型怎麼畫」，責任清楚，品質可控。
2. B 的成本為零、延遲為零、不會失敗，是「最低成本、高穩定度」的唯一解。
3. Structured Output 讓 AI 只能從 enum 選代碼（見 `analysis-schema.json`），前端永遠找得到對應圖層，不會出現「AI 說了一個圖庫沒有的位置」。
4. C 保留了 B 的所有優點，只是把座標從固定改成依特徵點計算，可漸進升級。

## 3. 方案 B 的實作設計

### 3.1 圖庫結構

以「臉型」為唯一索引，其他變數只影響**顏色與文字**，把組合數壓到最小：

```
assets/diagrams/
├── base/                 # 6 個臉型的底圖（線稿臉、含眉眼鼻唇，中性、無膚色）
│   ├── round.svg
│   ├── square.svg
│   ├── oval.svg
│   ├── diamond.svg
│   ├── heart.svg
│   └── oblong.svg
└── layers/               # 每個臉型 3 個圖層，同一 viewBox，座標對齊底圖
    ├── round/blush.svg   contour.svg   highlight.svg
    ├── square/...
    └── ...（共 18 個小 SVG）
```

規格：
- 統一 `viewBox="0 0 600 720"`，臉置中，眼睛連線在 y≈300，方便所有圖層對齊。
- 圖層內每個區塊有 `id`（對應 schema 的 enum，如 `id="cheek_hollow"`、`id="apple_center"`），前端可**依 AI 回傳的 zones 陣列只顯示對應區塊**，同一臉型的圖層可覆蓋多種建議。
- 顏色不寫死，用 `fill="currentColor"` 或 CSS 變數（`--blush`、`--contour`、`--highlight`），前端依季型把 `makeup.blush.hex` 填進去 → 腮紅顏色也是個人化的。
- 圖層用半透明（`opacity 0.55`）+ 柔邊（`<feGaussianBlur stdDeviation="6">`），看起來像真的暈染而非色塊。

### 3.2 對照表（由 Han 定義，前端與系統提示共用）

| 臉型 | 腮紅 placement | 修容 zones | 打亮 zones | 一句畫法 |
|---|---|---|---|---|
| round 圓臉 | `cheekbone_diagonal`（斜向上拉長） | `cheek_hollow`, `jawline`, `hairline_sides` | `forehead_center`, `chin_center`, `nose_bridge` | 腮紅由蘋果肌斜刷向太陽穴，拉出縱向線條 |
| square 方臉 | `apple_center` 圓刷（柔化） | `jaw_corners`, `forehead_sides`, `temples` | `cheekbone_top`, `forehead_center`, `chin_center` | 修容集中在下顎角與額角，腮紅圓刷增加柔和感 |
| oval 鵝蛋臉 | `apple_outer` | `cheek_hollow`（輕） | `cheekbone_top`, `under_brow`, `cupid_bow` | 比例已均衡，重點放在打亮提升立體度 |
| diamond 菱形臉 | `under_eye_wide` 橫向、偏內 | `temples`, `cheek_hollow`（顴骨下）, `chin_tip` | `forehead_center`, `chin_center`, `inner_eye` | 用打亮補額頭與下巴的寬度，修容收顴骨 |
| heart 心形臉 | `horizontal_mid` 橫向、位置略低 | `temples`, `forehead_sides`, `chin_tip` | `chin_center`（橫向拉寬）, `cheekbone_top` | 額頭兩側收窄、下巴打亮放寬，平衡上寬下尖 |
| oblong 長臉 | `horizontal_mid` 橫向平刷 | `hairline_top`, `chin_tip` | `cheekbone_top`（橫向）, `under_brow` | 上下修容縮短臉長，腮紅橫刷增加寬度 |

> 這張表是「專業資產」，建議 Han 親自審定，之後同一份表放進 AI 系統提示（作為 AI 選代碼的理由）與前端（作為文字說明）。

### 3.3 前端元件

```jsx
// FaceDiagram.jsx（概念）
export function FaceDiagram({ faceShape, makeup, activeLayers }) {
  const Base = BASES[faceShape];                 // 內聯 SVG（vite-plugin-svgr 或 ?raw）
  return (
    <svg viewBox="0 0 600 720" className="w-full max-w-sm">
      <Base />
      {activeLayers.blush && (
        <Layer src={LAYERS[faceShape].blush} visibleIds={[makeup.blush.placement]}
               style={{ "--blush": makeup.blush.hex }} />
      )}
      {activeLayers.contour && (
        <Layer src={LAYERS[faceShape].contour} visibleIds={makeup.contour.zones} />
      )}
      {activeLayers.highlight && (
        <Layer src={LAYERS[faceShape].highlight} visibleIds={makeup.highlight.zones} />
      )}
    </svg>
  );
}
```

- `Layer` 讀入 SVG，對每個 `<g id>` 依 `visibleIds` 設 `display`。
- 三個圖層各有開關 chip（腮紅 / 修容 / 打亮），下方顯示對應的 `tip` 文字。
- 圖層淡入動畫（CSS `opacity` transition 300ms）增加「被畫上去」的感覺。
- 分享卡與 Flex Message 縮圖：用同一 SVG 在 Canvas 畫成 PNG（`<img src=data:svg>` → `drawImage`），不需另做圖。

### 3.4 設計工作量

| 項目 | 數量 | 預估 |
|---|---|---|
| 底圖臉型線稿 | 6 | 2 天（可由一張基礎臉變形） |
| 圖層（每臉型 blush / contour / highlight，各含所有可能區塊） | 18 | 3 天 |
| 風格標籤示意小圖 | 10 | 1 天 |
| 分享卡版型 | 1–2 | 1 天 |

## 4. 方案 C（Phase 2）的技術路徑

1. 拍照頁已載入 MediaPipe（品質檢查用），改用 **Face Landmarker**（同一套 wasm，多 478 個特徵點與臉部轉換矩陣）。
2. 每個圖層區塊改用「錨點定義」而非固定座標，例如：
   - 腮紅 `cheekbone_diagonal`：以特徵點 #50（左蘋果肌）到 #234（太陽穴附近）為長軸的橢圓，短軸 = 兩眼距 × 0.45。
   - 修容 `jaw_corners`：沿特徵點 #172 → #136 → #150 的下顎輪廓向內偏移 8% 臉寬的帶狀。
3. 以 Canvas 在客人照片上疊半透明形狀 + 高斯模糊，輸出「你的臉上的畫法」；偵測失敗或側臉角度 > 15° 則退回 B 的示意圖。
4. 照片仍不上傳（特徵點在客端），個資風險不增加；但**分享卡若含客人照片需再次確認**。

預估工程量：2–3 週（含 6 臉型的錨點調校與真人測試）。

## 5. 為什麼不做方案 A（即使未來也不建議）

- 生成模型對「位置語意」不可靠，會把修容畫到錯的地方，專業信譽反而受損。
- 每次生成都是新圖，客人回頭看會發現「怎麼跟上次不一樣」。
- 要把照片送到第三方生成服務，隱私與內容審核風險最高。
- 若未來要做「虛擬試妝」（試唇色 / 眼影），也應走 C 的路線（特徵點 + 顏色混合），而非生成。
